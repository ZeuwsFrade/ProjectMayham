# Система квестов — спецификация

Дата: 2026-10-10. Статус: согласована 2026-10-10, реализована 2026-10-11; план работ — `Docs/superpowers/plans/2026-10-11-quest-system.md`.
После итоговой проверки кода уточнены разделы 4.1, 7 и 10 (страницы не длиннее трёх строк, фраза «всё готово», проверка выдающего, количество в награде).

## 1. Цель

Замкнуть основной цикл игры из концепта: взять квест у NPC → рейд → лут → вернуться → закрыть квест.
Первая версия: квесты от Тайлера в убежище, три типа целей, цепочки, награды, сохранение прогресса.

Сейчас в коде есть только заглушка `QuestService.GetAvailable`, которая всегда возвращает пустой список,
и реплика Тайлера «Есть для меня работа?», ведущая к ответу «Работы пока нет».

## 2. Решения, принятые заранее

| Вопрос | Решение |
|---|---|
| Типы целей | Принести обычные предметы; найти особый предмет, который появляется в рейде только пока квест активен; побывать в комнате нужного вида и вернуться живым |
| Структура | У квеста есть условие «открывается после таких-то»; активных квестов может быть несколько; взять можно всё, что предлагают |
| Интерфейс | Журнала и постоянной строки на экране нет. Квесты выдаёт, напоминает и принимает Тайлер в диалоге. Единственное исключение — короткая надпись в рейде, когда нужное место отмечено |
| Кто выдаёт | Тайлер. Квест привязан к идентификатору NPC, чтобы позже добавить других |
| Награды | Деньги и/или предметы |
| Кто наполняет | Сценарист в Инспекторе Unity, без программирования |
| Объём | Сбалансированный: основа, проверка квестов из меню, удобный ввод целей, меню «новый квестовый предмет», разбивка длинных реплик на страницы |
| Тестовый круг | `TileTest` возвращает игрока в `ShelterTest` |

Не входит в первую версию: журнал квестов, цель «убить врагов» (под неё только резервируется номер типа),
отказ от квеста, провал, таймеры, повторяемые квесты, окно-обзор цепочек, предпросмотр реплик в Инспекторе.

## 3. Обзор

| Часть | Где | Что делает |
|---|---|---|
| `QuestDefinition` | `Assets/Scripts/Quests` | Ассет одного квеста: кто выдаёт, условия, цели, тексты, награда |
| `QuestObjective` | там же | Одна цель квеста |
| `QuestGiverDefinition` | там же | Ассет NPC, выдающего квесты: его общие фразы |
| `QuestCatalog` | там же | Находит все ассеты квестов и выдающих |
| `QuestLog` | там же | Все правила: состояние квеста, взять, проверить, сдать, что нужно в рейде, засчитать места |
| `QuestText` | там же | Разбивка реплик на страницы, строки «Нужно…», «Награда…» |
| `QuestDialogue` | там же | Строит разговор о работе из узлов существующего окна диалога |
| `RaidQuestTracker` | там же | В рейде отмечает посещённые комнаты, показывает надпись, при возвращении передаёт отметки |
| `QuestService` | существующий файл | Меняется только тело `GetAvailable` |
| `RaidDemands` | `Assets/Scripts/Level` | Что квесты требуют от рейда: какие комнаты и какие особые предметы |
| `QuestValidator`, `QuestObjectiveDrawer`, `QuestMenus` | `Assets/Editor/Quests` | Проверка данных, удобный ввод целей, создание квестового предмета |

`QuestLog` не хранит своего состояния: каждый вызов читает `GameSession.Data`. Поэтому «Новая игра»
и «Загрузить» работают без дополнительных действий.

## 4. Данные

### 4.1. `QuestDefinition`

`ScriptableObject`, меню `Mayham/Quests/Quest`. Идентификатор квеста — имя ассета (`Id => name`), как у предметов и торговцев.
Ассеты лежат в `Assets/Resources/Quests/<имя NPC>/`, например `Assets/Resources/Quests/Tyler/Tyler_01_Papers.asset`.

Поля в порядке, в котором они нужны в игре:

| Поле | Тип | Назначение |
|---|---|---|
| `giver` | `QuestGiverDefinition` | Кто выдаёт и принимает |
| `requires` | `List<QuestDefinition>` | Квест открывается, когда все перечисленные сданы. Пусто — доступен сразу |
| `order` | `int` | Порядок в списке предложений (меньше — раньше), при равенстве — по имени |
| `title` | `string` | Короткое название, стоит на кнопке ответа |
| `offerText` | `string` (TextArea) | Что Тайлер говорит, предлагая квест |
| `objectives` | `List<QuestObjective>` | Цели |
| `reminderText` | `string` (TextArea) | Что он говорит, пока квест не выполнен. Пусто — общая фраза выдающего |
| `completedText` | `string` (TextArea) | Благодарность при сдаче |
| `rewardMoney` | `int`, не меньше 0 | Деньги |
| `rewardItems` | `List<ItemAmount>` | Предметы; класс `ItemAmount` уже есть в `ProjectMayham.Trade`. Количество меньше 1 (например, не заполненное в Инспекторе) считается за 1, как у целей |

Переименование ассета меняет идентификатор и сбрасывает прогресс по этому квесту, поэтому порядок задаётся полем `order`, а не именем.

### 4.2. `QuestObjective`

Обычный `[Serializable]`-класс.

| Поле | Используется для | Назначение |
|---|---|---|
| `kind` | всех | `Deliver = 0`, `FindSpecial = 1`, `VisitRoom = 2`. Номера заданы явно; `3` зарезервирован под убийства |
| `item` | `Deliver`, `FindSpecial` | Какой предмет |
| `count` | `Deliver`, `FindSpecial` | Сколько штук, не меньше 1 |
| `room` | `FindSpecial`, `VisitRoom` | Вид комнаты (`RoomKind`): где лежит особый предмет или куда нужно дойти |
| `text` | всех | Своя формулировка цели. Пусто — формулировка строится автоматически |

Автоматическая формулировка (`Describe()`): «Папки ×3», «Красная папка (Офис босса)», «Побывать: Парковка».
В строке прогресса используется та же формулировка без количества (`Subject`): «Папки — 2/3».
Названия берутся из `ItemDefinition.DisplayName` и `RoomSizes.Title`.

Ключ отметки посещения: `"visit:" + имя значения RoomKind`, например `visit:Parking`.

### 4.3. `QuestGiverDefinition`

`ScriptableObject`, меню `Mayham/Quests/Quest Giver`. Имя ассета — идентификатор NPC; для торговца оно совпадает
с `TraderDefinition.Id` (`Tyler`). Лежит в `Assets/Resources/Quests/Givers/`.

Поля — общие фразы, у каждой есть значение по умолчанию:

| Поле | По умолчанию |
|---|---|
| `askChoice` | «Есть для меня работа?» |
| `menuText` | «Есть пара дел.» |
| `noWorkText` | «Работы пока нет, [ИГРОК]. Загляни позже.» |
| `acceptedText` | «Договорились.» |
| `reminderText` | «Ты ещё не всё сделал.» |
| `readyText` | «Вижу, всё при тебе.» |
| `noRoomText` | «Тебе некуда положить награду. Освободи место и приходи.» |

Подписи ответов игрока («Берусь», «Не сейчас», «Вот, держи», «Позже», «Понятно», «Дальше», «Что ещё?», «Назад»)
одинаковы для всех NPC и заданы константами в `QuestDialogue`.

### 4.4. Особый предмет

Обычный `ItemDefinition` в `Assets/Data/Items/Quest/` с ценой (`value`) 0 и своим префабом-подбираемым предметом.
Цена 0 обязательна: `TraderBook.SellPrice` тогда возвращает 0 и продать предмет Тайлеру нельзя.
Иначе проданный предмет считался бы «не у игрока», в следующем рейде появился бы второй, а первый можно было бы выкупить.

### 4.5. `QuestCatalog`

Статический класс. Один раз загружает `Resources.LoadAll<QuestDefinition>("Quests")` и
`Resources.LoadAll<QuestGiverDefinition>("Quests")`; кеш сбрасывается при запуске игры
(`RuntimeInitializeLoadType.SubsystemRegistration`, как в `GameSession`).

- `All` — все квесты; `Find(id)`; `ByGiver(npcId)` — квесты выдающего по `order`, затем по имени; `Giver(npcId)`.
- Квест, который нельзя вычислить (нет выдающего, цель `Deliver`/`FindSpecial` без предмета), пропускается
  с одним предупреждением в консоли: он не предлагается и ничего не ломает.

## 5. Состояние и сохранение

В `Assets/Scripts/Core/SaveData.cs` добавляются класс и поле; номер версии сейва не меняется:

```csharp
[Serializable]
public class QuestProgressData
{
    public string quest;                              // идентификатор квеста
    public int state;                                 // 1 — взят, 2 — сдан
    public List<string> marks = new List<string>();   // отметки, например "visit:Parking"
}

public List<QuestProgressData> quests = new List<QuestProgressData>();
```

Порядок записей — порядок, в котором квесты брали. Прогресс по предметам не хранится: это содержимое рюкзака.

Состояния квеста (`QuestLog.QuestStatus`):

| Состояние | Когда |
|---|---|
| `Locked` | Не все квесты из `requires` сданы |
| `Available` | Условия выполнены, записи в сейве нет |
| `Active` | Запись с `state = 1` |
| `TurnedIn` | Запись с `state = 2` |

Когда что меняется:

| Событие | В памяти | В файле |
|---|---|---|
| Игрок взял квест | добавляется запись `state = 1` | при ближайшем обычном сохранении (уход из убежища, сон) |
| Вошёл в нужную комнату в рейде | только список в `RaidQuestTracker` | ничего |
| Вернулся из рейда живым | отметки переносятся в записи квестов | тем же сохранением, которым пишется рюкзак |
| Погиб | ничего | сохранение по пути в убежище, без отметок |
| Сдал квест | предметы убраны, награда выдана, `state = 2` | при ближайшем обычном сохранении, как при торговле |

Старые и странные сейвы:

- Нет поля `quests` — `QuestLog` обращается к списку через метод, который создаёт его при отсутствии. Результат: ничего не взято, предлагаются квесты без условий.
- Запись о квесте, ассета которого нет, — пропускается, но остаётся в файле.
- Две записи об одном квесте — действует первая.
- Отметки для целей, которых больше нет, — игнорируются.

## 6. Правила (`QuestLog`)

Статический класс без собственного состояния.

| Метод | Что делает |
|---|---|
| `StatusOf(quest)` | Состояние квеста |
| `Offers(npcId)` | Квесты выдающего в состоянии `Available` |
| `ActiveOf(npcId)` | Квесты выдающего в состоянии `Active` |
| `Accept(quest)` | Берёт квест, если он `Available`. Повторный вызов ничего не меняет |
| `Check(quest, backpack, stash = null)` | Прогресс по каждой цели: сколько есть, сколько нужно, выполнена ли, сколько лежит в тайнике; и общий признак «готов к сдаче» |
| `TryTurnIn(quest, backpack)` | Сдаёт квест, см. ниже. Возвращает `TurnInResult`: `Done`, `NotActive`, `NotReady`, `NoRoom` |
| `BuildRaidDemands()` | Что активные квесты требуют от рейда, см. раздел 8 |
| `CommitVisits(kinds)` | Ставит отметки посещения активным квестам, которым они нужны. Повторная отметка ничего не меняет |

**Подсчёт предметов.** В рюкзаке: `GridInventory.CountOf(item)` плюс один, если этот предмет в руках
(`HeldItem`) — `CountOf` руки не учитывает. Для сдачи считается только рюкзак и руки, тайник не считается.
Если нужный предмет лежит в тайнике, `Check` сообщает сколько, чтобы Тайлер мог это сказать.

**Сдача (`TryTurnIn`).** Всё или ничего, по схеме `TraderBook.TryBarter`:

1. Квест должен быть `Active` (иначе `NotActive`), а `Check` — показывать готовность (иначе `NotReady`).
2. Снимок рюкзака: `backpack.Export()` (включает предмет в руках).
3. Для каждой цели с предметом: `RemoveItems(item, count)`; если не хватило одной штуки и предмет в руках — `TakeHeld`.
4. Выдача предметов награды через `Add`. Если что-то не влезло по месту или весу — `backpack.Import(снимок)`, результат `NoRoom`; Тайлер отвечает фразой `noRoomText`.
5. `GameSession.AddMoney(rewardMoney)`, запись получает `state = 2`.

Отдельной записи файла при сдаче нет: до следующего сохранения предметы, деньги и состояние меняются только
в памяти и при сбое откатываются вместе.

**`QuestService.GetAvailable(npcId)`** сохраняет сигнатуру и возвращает названия квестов из `QuestLog.Offers(npcId)`.

## 7. Разговор с Тайлером

Окно диалога (`DialogueWindow`) не меняется. Его пределы: три ответа на узел и примерно три строки текста
(поле 1440×120 при размере шрифта 30, лишнее обрезается многоточием). Дизайн укладывается в эти пределы.

В `NpcTrader.Interact` блок, который строит узел «работы нет», заменяется одной строкой:

```csharp
root.Choices.Add(QuestDialogue.WorkChoice(trader.Id, inventory, root));
```

Ответы «Давай посмотрим товары» и «Я пойду» остаются.

Каждый узел строится в момент выбора ответа, поэтому числа верны и после торговли в том же разговоре.
Это опирается на то, что `DialogueWindow.Pick` сначала вызывает `Action` ответа и только потом читает `Next`.

**Список дел.** Ответ «Есть для меня работа?» открывает список:

- Темы идут в порядке: готовые к сдаче, новые, в работе. Подписи: «Сдать: <название>», «Новое дело: <название>», «Напомни: <название>».
- На странице две темы; третий ответ — «Что ещё?» (следующая страница) или, на последней, «Назад» в начало разговора.
- Текст узла — `menuText`. Если тем нет: `noWorkText` и один ответ «Понятно».

**Предложение.** Страницы `offerText`, у каждой один ответ «Дальше». Затем отдельная страница, собранная игрой,
уменьшенным шрифтом, в две строки: «Нужно: Бумаги ×3» и «Награда: 30 $», с ответами «Берусь» и «Не сейчас».
«Берусь» берёт квест, показывает `acceptedText` и возвращает в список. «Не сейчас» возвращает в список.

**Напоминание.** `reminderText` квеста или общая фраза, затем строка прогресса:
«Папки — 2/5; Красная папка (Офис босса) — 0/1, в тайнике: 1; Побывать: Парковка — ещё нет». Один ответ «Понятно».

**Сдача.** `readyText` и строка прогресса, ответы «Вот, держи» и «Позже». Короткая фраза в одну строку стоит на одном экране
со строкой прогресса; длинная или многострочная произносится сначала (по страницам, ответ «Дальше»), а прогресс
с двумя ответами идёт отдельной страницей — то, что будет забрано, всегда видно.
Успех: страницы `completedText`, затем «Получено: 30 $, Кружка» (если награда есть; «×N» пишется только при N больше 1) и обновлённый список,
где квесты, открытые этой сдачей, уже видны как новые. Неудача: `noRoomText`, квест остаётся активным.

**Страницы (`QuestText.Pages`).** Сценарист разделяет страницы пустой строкой. Окно показывает три строки, поэтому
страница, в которой больше трёх строк, продолжается на следующей после каждой третьей. Страница длиннее 230 символов
дополнительно делится по концу предложения, а если его нет — по последнему пробелу. Строки, собранные игрой,
всегда идут отдельной страницей. Подстановка `[ИГРОК]` уже работает в окне диалога.

Тайник для строки «в тайнике: N» берётся из живого `StashChest.Inventory` в сцене убежища.

## 8. Рейд

### 8.1. Что квесты требуют от рейда

`RaidDemands` — простой класс в `Assets/Scripts/Level`, не зависящий от квестов:

- `Items` — список «предмет, сколько, в комнате какого вида»;
- `Visits` — набор видов комнат, которые нужно посетить;
- `Rooms` — объединение видов комнат из обоих списков.

`QuestLog.BuildRaidDemands()` проходит активные квесты в порядке, в котором их брали:

- цель `VisitRoom` без отметки добавляет вид комнаты в `Visits`;
- цель `FindSpecial` считает, сколько штук предмета уже есть у игрока — в сохранённом рюкзаке, в руках и в тайнике
  (`GameSession.Data.player` и `Data.stash`), — и добавляет недостающее в `Items`;
- цель `Deliver` ничего не добавляет.

Данные актуальны: `SceneLoader.Load` сохраняет игру до загрузки сцены рейда, а генератор работает раньше, чем игрок получает рюкзак.

### 8.2. Генератор рейда

Изменения в `RaidGenerator` и `RoomLibrary`:

- `Generate(int seed, RaidDemands demands = null)`. В игре `Awake` передаёт `QuestLog.BuildRaidDemands()`.
  Предпросмотр в редакторе требований не передаёт и работает как раньше.
- Новый шаг `AssignRequiredKinds` перед заполнением слотов. Для каждого нужного вида комнаты выбирается свободный слот,
  в который вид помещается; сначала виды с наименьшим числом подходящих слотов (парковка подходит только в большие).
  Остальные слоты заполняются как раньше.
- `RoomLibrary.CanPlace(kind, size)`: размер разрешён для вида и есть префаб. Вес не учитывается, поэтому редкая комната
  может быть гарантирована.
- `PlaceRoom` получает необязательный принудительный вид.
- **Без требований шаг не тянет случайных чисел**: рейд без активных квестов с тем же сидом совпадает с нынешним.
  С требованиями одинаковые сид и требования дают одинаковый рейд.
- Вид, для которого не нашлось слота или префаба: предупреждение в консоли, квест в этом рейде не продвигается.

### 8.3. Особый предмет

В `SpawnRoomLoot` принудительно поставленная комната сначала раскладывает нужные квестам предметы по случайным
точкам лута, и обычный лут на эти точки не кладётся. Предмет создаётся как его `WorldPrefab` с `ItemPickup.Set(item, count)`.

Что происходит с предметом дальше:

| Ситуация | В следующем рейде |
|---|---|
| Остался лежать в рейде | появится снова |
| Был в рюкзаке или в руках, игрок погиб | появится снова |
| Лежит в рюкзаке, в руках или в тайнике | не появится; про тайник Тайлер скажет |
| Выброшен на пол в убежище (пол не сохраняется) | появится снова |
| Сдан | квест закрыт, больше не появляется |

Второй экземпляр появиться не может: количество в рейде всегда равно «нужно минус есть».

Если у комнаты нет точек лута: предупреждение, предмет не создаётся. Проверка квестов ловит это заранее.

### 8.4. Посещение и надпись

`RaidQuestTracker` — компонент, который генератор добавляет сам при запуске рейда; в сцены ничего не ставится.

- Каждый кадр сравнивает положение игрока с прямоугольниками размещённых комнат. Расстояние до центра комнаты
  считается через `WrapWorld.Active.Delta`, поэтому проверка верна и через шов карты. Засчитывается область
  внутри комнаты с отступом в один тайл от стен: стоять в дверях недостаточно.
- Запоминает все виды комнат, в которых игрок побывал. Если вид нужен активному квесту (есть в `RaidDemands.Visits`),
  один раз показывает на пару секунд надпись «Отмечено: Парковка» вверху экрана.
- Подписан на `GameSession.SaveRequested`. В рейде сохранение происходит только при уходе из него.
  Если игрок жив (`PlayerStats.IsDead == false`), вызывает `QuestLog.CommitVisits`; если погиб или игрок не найден — ничего не пишет.

Место, посещённое в одном рейде и донесённое до убежища, остаётся засчитанным навсегда, даже если игрок погибнет в следующем.

## 10. Инструменты редактора

**`Mayham/Quests/Validate Quests`.** Сообщения на русском, с указанием ассета.

Ошибки:

- не указан выдающий; у цели `Deliver` или `FindSpecial` нет предмета; в награде пустой предмет;
- предмета нет в `ItemDatabase` (при загрузке сейва он бы молча пропал);
- особый предмет с ценой выше 0, либо он есть в таблице лута, в товарах или бартере торговца;
- у особого предмета нет префаба, либо на префабе нет `ItemPickup` или `WrapEntity`;
- для вида комнаты нет префаба ни одного разрешённого размера; для `FindSpecial` — у префаба нет точек лута;
- условие ссылается на удалённый ассет, на сам квест или образует цикл;
- два квеста с одинаковым именем; ассет лежит вне `Resources/Quests`;
- две цели одного квеста с одним и тем же предметом.

Предупреждения: страница длиннее 230 символов или трёх строк; нет целей; пустое название, предложение или благодарность;
нет награды; предмет для `Deliver` не встречается ни в луте, ни у торговца.
По выдающему: его имя не совпадает ни с одним NPC (сейчас — с именем ассета торговца), тогда его квесты никто не предложит;
фраза над списком дел или «работы нет» не помещается на одну страницу; остальные его фразы — те же проверки длины, что у квеста.

**Ввод цели в Инспекторе.** Для цели показываются только поля её типа; виды комнат подписаны по-русски.

**`Mayham/Quests/New Quest Item`.** Спрашивает имя (оно же идентификатор предмета), создаёт предмет с ценой 0
в `Assets/Data/Items/Quest`, его префаб (копия существующего подбираемого предмета) и обновляет базу предметов.
Префаб, который уже принадлежит другому предмету, не переиспользуется.

**Самопроверки.** `Mayham/Quests/Run Self-Test` — правила на данных в памяти; `Check Raid Demands` — генератор на 30 сидах
(нужна открытая сцена рейда); `Check Quest Tools` — создание квестового предмета на временных ассетах.

## 13. Краевые случаи

| Случай | Поведение |
|---|---|
| Игрок дошёл до места и погиб | Отметка не пишется, место нужно посетить снова |
| Выход из игры посреди рейда | Сохранения не было: рюкзак, отметки и особый предмет откатываются вместе |
| Двум активным квестам нужен один обычный предмет, а хватает на один | Оба показываются готовыми; после сдачи одного второй пересчитывается и снова «в работе» |
| Нужный предмет в руках | Считается и забирается |
| Награда не влезает | Рюкзак восстанавливается, деньги не выдаются, квест остаётся активным |
| Квест взят, когда особый предмет уже есть у игрока | В рейде предмет не появляется, цель сразу выполнена |
| Место посещено, когда квест не был активен | Не считается: отметки ставятся только активным квестам в момент возвращения |
| Нужных видов комнат больше, чем подходящих слотов | Предупреждение; не поместившийся вид достанется квесту в одном из следующих рейдов |
| Повторное нажатие «Берусь» или «Вот, держи» | Второй вызов ничего не меняет |
| «Новая игра» после игры | Состояние квестов читается из нового сейва, от прошлой игры ничего не остаётся |

## 14. Проверка

В проекте нет сборок с автотестами, поэтому правила проверяются самопроверкой из меню `Mayham/Quests/Run Self-Test`
(она работает на данных в памяти и не трогает файл сохранения), а остальное — как для уровня: скриптами в редакторе и запуском сцен.
Файл сохранения перед прогонами копируется и после них возвращается.

1. Проверка квестов из меню проходит на тестовом содержимом без ошибок; на специально испорченных данных
   (цена у особого предмета, цикл в условиях) выдаёт соответствующие ошибки.
2. В редакторе, 30 сидов: без требований набор комнат совпадает с тем, что было до изменений; с требованиями
   «офис босса и парковка» нужные виды есть в каждом рейде, особый предмет создан ровно один раз; все участки достижимы.
3. В игре, круг `ShelterTest` → `TileTest` → `ShelterTest`:
   - Тайлер предлагает два квеста, оба берутся; напоминание показывает прогресс;
   - сдача «Бумаг» выдаёт деньги и открывает квест про красную папку;
   - в рейде есть офис босса с красной папкой; после возвращения с ней квест сдаётся;
   - папка, положенная в тайник, в рейде не появляется, Тайлер говорит про тайник;
   - на парковке появляется надпись; возвращение живым засчитывает место, смерть — нет;
   - награда, которая не влезает, не выдаётся и квест остаётся активным.
4. Старый сейв без квестов загружается, квесты предлагаются с начала.

## 15. Известные следствия

- `MainScene` не редактируется, но код генератора общий: гарантия комнат, особые предметы и отметки посещений
  заработают и в её лабиринте, когда игрок выйдет в рейд из настоящего убежища.
- Особый предмет лежит на обычной точке лута среди других вещей и никак не подсвечен: комнату придётся осмотреть.
  Отдельные «квестовые» точки в префабах комнат — возможное улучшение позже.
